# REA Lab — primeira versão do fluxo Projetos 2.0

Data: 16/10/2026. Desenho conceitual e especificação detalhada aprovados explicitamente pelo usuário neste chat após revisão. Aprovação registrada no projeto, sem alterar arquivos da skill Superpowers. Não representa funcionalidades implementadas.

## Objetivo e entrega

Transformar a CLI existente em uma ferramenta local que organiza a análise de um projeto e a construção de uma alternativa independente chamada `<nome>-2.0`. A primeira entrega cobre um alvo JavaScript local por vez, tarefas persistentes, relatórios e preparação de repositório Git. Não promete reconstruir qualquer aplicativo automaticamente.

O programa deve tornar visíveis os passos entre analisar, especificar, implementar e validar. Um repositório criado ou um processo com saída zero não prova equivalência funcional. A meta é software próprio utilizável, com melhorias demonstradas por testes comparáveis.

## Base existente e limites

- CLI Node.js com inventário, análise REA, diagnóstico MCP e evidências em arquivos.
- REA fixado em 6.5.0; integração JavaScript com teste semântico próprio existente.
- Ghidra instalado em ambiente anterior, sem aceitação real de análise binária neste fluxo.
- Catálogos ECC e forks são referências; não são adaptadores automaticamente ativos.
- Dez testes e diagnóstico MCP passaram na consulta anterior deste chat. São evidências datadas, não garantia de disponibilidade futura.

## Decisões de arquitetura

Expandir a CLI existente é preferível a reconstruir outro motor ou instalar um orquestrador externo completo: reaproveita a integração testada e mantém o escopo verificável. Um painel gráfico e adaptadores adicionais serão entregas posteriores sobre os mesmos arquivos de estado.

O primeiro incremento usa Node.js e o motor já fixado. Não exige Docker, WSL, Plandex ou API paga. O Plandex serve como referência de tarefas, contexto seletivo e revisão das diferenças; não será dependência desta entrega. Implementação do novo produto continua assistida pelo Codex e revisada pelo usuário, sem um agente autônomo permanente.

## Componentes e contratos

1. **CLI de projetos:** valida parâmetros e apresenta estados em português e JSON. Novos subcomandos sob `lab project` não alteram a semântica dos comandos atuais.
2. **Armazenamento local:** guarda manifesto, tarefas e execuções fora do repositório gerado. Escritas usam arquivo temporário e renomeação no mesmo diretório. Um bloqueio exclusivo impede dois escritores; bloqueio remanescente informa o problema e não é removido automaticamente.
3. **Adaptador JavaScript:** chama a integração REA existente; seleciona explicitamente fontes, preserva saída completa e verifica sua associação aos hashes. Não executa arquivos do alvo.
4. **Relatório de cobertura:** distingue inventário, análise semântica, validação do produto e comparação de desempenho. Falha ou limite fica registrado, sem promoção a sucesso.
5. **Preparação Git:** cria diretório novo com sufixo `-2.0`, documentação e repositório independente. Não copia automaticamente o código ou binários do alvo. Não altera o original e não sobrescreve diretórios existentes.

## Comandos propostos

Os nomes abaixo definem a interface a implementar; ainda não estão disponíveis.

```text
npm.cmd run lab -- project create <alvo> --name <nome> --workspace <pasta-nova> --mode <independent|reuse>
npm.cmd run lab -- project analyze <workspace> --source-path <arquivo-relativo>
npm.cmd run lab -- project status <workspace> --json
npm.cmd run lab -- project task add <workspace> --title <titulo> --acceptance <criterio> [--depends-on <id>]
npm.cmd run lab -- project task set <workspace> <id> --state <estado> [--evidence <arquivo>]
npm.cmd run lab -- project report <workspace>
npm.cmd run lab -- project prepare-repo <workspace> --output-parent <pasta>
```

O nome recebe normalização explícita para nome GitHub: letras latinas, números, ponto, hífen e sublinhado. A CLI mostra o nome final; entrada vazia ou sem caracteres válidos falha. Remove-se apenas um sufixo terminal `-2.0` antes de acrescentá-lo, evitando duplicação. Conflitos exigem outro nome ou destino; nunca criam uma sequência silenciosa.

`--depends-on` pode ser repetido para registrar várias dependências. `--mode independent` registra reconstrução independente; `reuse` exige documentar origem e licença antes da exportação. A análise aceita as opções de prazo e memória já implementadas pela integração; valores inválidos falham antes de iniciar o motor. Identificadores de tarefa são gerados pela ferramenta e não podem conter caminhos.

## Dados e persistência

O workspace é uma pasta nova separada do alvo e do repositório de saída. Nem ele nem o destino podem estar dentro do alvo. Links simbólicos e pontos de redirecionamento encontrados em caminhos de escrita são recusados. Comparações consideram separadores, limites entre componentes e caixa do Windows.

```text
workspace/
  project.json
  tasks.json
  events.jsonl
  runs/<id>/
  reports/
```

`project.json` contém `schemaVersion: 1`, UUID, nome original, nome final, caminho local do alvo, formato, revisão Git quando disponível, hashes das fontes selecionadas, datas UTC, modo de implementação e referência opcional ao destino. Caminhos privados ficam somente no workspace.

`tasks.json` contém IDs estáveis, título, dependências, critérios de aceitação e estado: `pending`, `running`, `blocked`, `done` ou `failed`. Dependências devem existir e formar grafo sem ciclos. Uma tarefa só entra em `running` com dependências concluídas. `done` exige evidência; tarefa com dependentes em execução ou concluídos não pode retroceder sem atualização explícita deles. Conclusão manual é rotulada como declaração do operador, separada da validação automática.

Evidência de conclusão é um arquivo regular dentro do workspace, sem redirecionamentos, registrado por caminho relativo e SHA-256. Sua existência não prova o critério: o relatório identifica se houve validação automática ou declaração manual. Alteração posterior do hash invalida a referência no relatório. A operação `task set` não executa o conteúdo do arquivo.

Cada execução tem ID próprio, hashes das entradas, versões, opções, início/fim, exit code, motivo de interrupção e referências a stdout/stderr. O diário é informativo; manifestos são a autoridade para retomada. Se houver falha entre estado e diário, a próxima abertura relata divergência sem declarar execução concluída.

## Fluxo do usuário

1. Selecionar alvo e criar workspace; identificar formato e inventariar metadados sem executar o alvo.
2. Selecionar fontes e executar análise JavaScript. Cada execução usa pasta nova e prazos limitados.
3. Conferir cobertura e produzir especificação de comportamento. O programa cria estrutura documental; a especificação exige trabalho e revisão, não é inferida como verdade a partir de um grafo.
4. Registrar tarefas pequenas com critérios verificáveis e dependências; retomar pelo estado persistido.
5. Preparar `<nome>-2.0` em destino separado com README, escopo, atribuições, manifesto exportável sem caminhos privados e `.gitignore`. Git deve estar disponível; falha de `git init` preserva os arquivos e informa preparação incompleta. Retentativa nesse destino exige inspeção, sem sobrescrita automática.
6. Implementar código novo no repositório gerado com revisão das alterações. Não executar scripts arbitrários do alvo ou tarefas com comandos embutidos nesta versão.
7. Validar o produto com testes próprios. Publicar no GitHub somente após conferir o conteúdo exportável.

## GitHub e gratuidade

Esta primeira versão prepara o repositório local. A criação remota será feita pelo Codex com ferramentas autenticadas disponíveis, para cada alvo escolhido, usando `<nome>-2.0`; inicialmente privado. O suporte à criação remota dentro da CLI será outro incremento. Uma falha de autenticação não deve impedir uso local.

Nenhum token entra no manifesto ou nos relatórios. Publicação não inclui alvo, workspace, evidências privadas ou configuração local. Código novo pode usar MIT; componentes reutilizados mantêm licenças e avisos correspondentes. Reconstrução independente e reutilização são modos declarados separadamente. Trocar nome ou número de versão não permite declarar código copiado como criado do zero.

O núcleo local não chama modelos e não impõe cobrança de software. Serviços externos opcionais podem ter custos próprios. Não há promessa de consumo de IA ilimitado ou percentual de economia.

## Falhas, retomada e cobertura

- Formato não suportado: inventário permitido, análise recusada com formato e adaptador ausente explícitos.
- Engine ausente, permissão negada ou hash divergente: estado `blocked`, preservando evidências e controles existentes.
- Prazo excedido: interromper o processo do engine conforme integração existente, marcar falha e preservar saída parcial. Não anunciar conclusão.
- Estados de execução, separados dos estados de tarefa: `running`, `completed`, `blocked`, `failed`, `interrupted` e `unknown`. Registrar PID, instante de início e identidade do processo quando a plataforma permitir. Confirmada a ausência do processo original, marcar `interrupted`; se não for possível verificar sua identidade ou atividade, marcar `unknown` e não iniciar outra execução automaticamente. Uma nova análise recebe novo ID. Não reutilizar resultado só por existir arquivo.
- Resultado REA parcial ou fonte divergente: não aceitar como análise semântica verificada.
- Melhoria: registrar mesma tarefa, mesmo conjunto de entradas, ambiente e métrica para ambas as versões. Sem acesso a uma baseline comparável, apresentar apenas medição própria.

## Critérios de aceitação

1. Fixture JavaScript própria gera workspace e tarefas sem modificar o alvo; hashes antes/depois confirmam preservação.
2. Estado persiste ao fechar e abrir a CLI; dependências inválidas e ciclos são recusados.
3. Análise real aceita grafo associado à fonte; mocks não contam como evidência de engine.
4. Timeout, permissão negada e saída parcial aparecem como falha/bloqueio e não concluem tarefas.
5. Repositório novo tem nome esperado e não contém caminhos locais, credenciais, código ou binários do alvo por cópia automática.
6. Colisões e caminhos redirecionados não sobrescrevem arquivos existentes; teste específico cobre limites entre caminhos Windows.
7. Testes da integração atual continuam passando. Testes de unidade e integração real são reportados separadamente por plataforma.
8. Um pequeno produto JavaScript próprio, com comportamento especificado e teste executável, demonstra o fluxo até execução. Isso valida apenas esse exemplo e ambiente.

O exemplo do item 8 será implementado e executado pelo desenvolvedor em ambiente autorizado; não é um executor de comandos integrado à CLI. Assim, sua demonstração não antecipa o módulo de execução isolada previsto para entrega posterior.
